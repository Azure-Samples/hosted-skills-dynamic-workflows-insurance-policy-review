# Customize

The sample separates workflow planning from deterministic policy and document logic.
Change the smallest layer that owns the behavior you need.

## Add a policy servicing request type

Request requirements are defined in `_CHANGE_REQUIREMENTS` in
[`src/tools/policy_review_tools.py`](../src/tools/policy_review_tools.py).

1. Add the change type, required document kinds, optional document kinds, and manual
   review notes.
2. Add tests for found and missing evidence in
   [`tests/test_policy_review_tools.py`](../tests/test_policy_review_tools.py).
3. Add an example request under `examples/`.
4. Redeploy with `azd deploy`.

Unknown change types already produce a decision-neutral packet with a warning. Adding
a fixture makes the evidence requirements specific to that request type.

## Add a document kind

Supported document metadata kinds are defined in `_DOCUMENT_REVIEW_GUIDANCE`.

1. Add the document kind and the manual checks a reviewer should perform.
2. Add it to the relevant request requirements.
3. Cover `received`, `missing`, and `expired` states in the tests.

The validator sets `in_scope: true` only for a kind present in that mapping. Other kinds
remain in the ordered fan-in as skipped entries.

## Replace fictional policy data

`load_policy_context` currently reads `_POLICIES`, a small in-memory fixture. Replace
that lookup with an approved policy system while preserving the workflow handler
contract:

- keep the handler synchronous for Dynamic Workflows v1
- accept one dictionary
- return JSON-serializable data
- surface lookup and authorization errors explicitly
- do not return a policy decision

The same pattern applies to `inspect_policy_document`, which currently checks message
metadata but does not open or authenticate a file. A production integration should
read from an approved document system and return evidence for human verification.

## Change the workflow plan

The planning instructions are in
[`src/main.agent.md`](../src/main.agent.md). The current six-task shape is:

1. validate the request
2. load policy context
3. inspect documents with bounded `for_each` and `when`
4. build the packet from the ordered aggregate
5. render HTML
6. publish the terminal Blob

When adding a workflow tool, put the handler under `src/tools/`, decorate it with
`@workflow_tool`, describe its input and output precisely, and grant only the tools the
skill should use. Keep side effects idempotent because a durable activity can execute
more than once.

Redeploy agent or tool changes with:

```bash
azd deploy
```

## Adjust fan-out

The sample limits requests to eight documents through `_MAX_DOCUMENTS`. Dynamic
Workflows public experimental v1 defaults to 50 total authored or materialized nodes
and maximum parallelism of 10.

If you change the sample limit, update:

- `_MAX_DOCUMENTS`
- the validator's `@workflow_tool` description
- tests and request examples
- the documentation that describes the bound

Keep the limit below your operational concurrency and downstream service constraints.

## Change the report

The HTML is generated by `render_policy_review_html`. You can change its layout,
labels, and additional decision-neutral evidence sections. Preserve:

- `review_status: human_review_required`
- `decision: null`
- the source-system verification notice
- the authorized human reviewer as decision owner

The publisher accepts a request-specific Blob name. It overwrites that stable
destination so retries do not create duplicate reports.

## Change the model

For a deployed environment, set the model deployment inputs before `azd up`:

```bash
azd env set FOUNDRY_MODEL <deployment-name>
azd env set FOUNDRY_MODEL_NAME <model-name>
azd env set FOUNDRY_MODEL_VERSION <model-version>
```

For local execution, update `FOUNDRY_PROJECT_ENDPOINT` and `FOUNDRY_MODEL` in
`src/local.settings.json`.
